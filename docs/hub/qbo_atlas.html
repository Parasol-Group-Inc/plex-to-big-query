01The fleet

Two modules · six services · three companies

There is no company-specific code anywhere in this project. Which company a service syncs is decided entirely by its environment variables — the realm ID and the three Secret Manager names. That is why adding Kaya and ODF took configuration and no code at all.

But not every client gets every pipeline. Two of the four record no invoices worth syncing, and they are the two largest. Which QBO entity carries a company's revenue is a fact about its business model and has to be measured — see section 07.

03The rotation window

The mechanism behind both outages

Intuit invalidates the old refresh token the instant it issues a new one. If the replacement is not stored, the pipeline is locked out permanently — recoverable only by a human re-authorising in the OAuth Playground. Everything between the refresh and the write is a window in which the only live copy of a credential exists in memory.

On 2026-09-02 a read timeout on a cosmetic company-name lookup landed in that window, and four pipelines stayed down for six days.

What the code now guarantees

  • — The persist is the very next statement after the refresh. Nothing that can raise goes between.
  • — update_secret() retries 5× with backoff, because it is itself inside the window.
  • — An invalid_grant retries once, after re-reading the secret: two services can share one token, and the other may have legitimately rotated it a second ago. Unchanged value means a dead token, and we stop rather than loop.
  • — A persist that ultimately fails does not abort the run. We are locked out of the next run either way; the access token is good for an hour, so today's data still lands.
  • — The token is never logged, even on total failure.
tested, not hoped

tests/test_token_rotation.py and tests/test_token_resilience.py fail if any of the five guarantees above is undone. The invalid_grant retry and the persist-failure path have never fired in production — which is the desired state.

04Why rotation looks broken when it isn't

Intuit's 24-hour reuse window

Refresh twice inside about a day and Intuit hands back the same refresh token. So token_rotated = false is the normal case, not a symptom — and a daily schedule sits right on the boundary, which is why rotation happens intermittently.

05How data lands

A truncating load quietly deleted history for months

The invoice query filters on MetaData.LastUpdatedTime — a 30-day window by default, at Jennilyn's request. That window was never the bug. Pairing it with a WRITE_TRUNCATE load was: every run replaced the whole table with just the recently-modified slice, so anything untouched for a month was deleted. QSM was down to 39 rows; PCS to 33.

per-client decision

DAYS_BACK is 30 for PCS and QSM — Jennilyn's requirement, not a default to tune. Kaya runs 0 (fetch everything, nightly) because its data feeds a marketing scorecard instead, and at 68 invoices a full fetch is a single page. The payoff: an exact mirror of QBO that cannot drift. A windowed fetch permanently misses any edit made while the pipeline was down, which after a six-day outage is not hypothetical.

06Kaya's two homes

Views over one copy, not a second pipeline

Kaya's QBO data also has to be reachable from marketing-dashboard-506920, alongside its Shopify, Walmart and ShipStation datasets. Both projects are BigQuery multi-region US, which makes the cheap answer the correct one.

07What Kaya's numbers actually say

The oddest thing in the whole project

Kaya's invoice pipeline is technically perfect and almost empty: 68 invoices worth $30k across eight years, one of them in 2026 for $951. Meanwhile the P&L shows $2.24M of income this year. Marketplace sellers get paid at the point of sale, so there is nothing to invoice — the revenue is in SalesReceipt, and AR Aging returns zero rows because no receivable ever exists.

ODF is the same lesson, harder

On Demand Fulfillment is the largest client on the platform and records zero revenue documents of any kind — no invoices, no sales receipts, not even a Payment. Its $12,303,996 of 2026 revenue arrives as 1,010 bank deposits, categorised straight to income with no customer-level document in between.

The confirmation is exact: the P&L's month-to-date income is $331,115.46, and September's deposits total $331,115.46. Same money, to the cent.

08Quirks & traps

Every one of these has actually cost time

  1. 01

    Two different 400s that mean opposite things

    invalid_client means the client pair is wrong and consumes nothing — your token is still good. invalid_grant means the token is dead and nothing in GCP can fix it. Same status code, no overlap in the fix. Always read the response body, which the app logs on its own line.

    cost: the first hour of the September diagnosis

  2. 02

    Never retype a credential — decode the Basic blob

    Kaya's dump listed its client ID as text and as base64, and they disagreed: l and I transposed at two positions. The typed one fails invalid_client.

    cost: this class of bug has bitten twice — also a 2/4 typo in July

  3. 03

    printf '%s', never echo

    echo appends a newline, and Intuit rejects the token with invalid_grant — indistinguishable from the bug you are trying to fix.

  4. 04

    GOOGLE_FUNCTION_SOURCE persists across redeploys

    The buildpack wants a file called main.py. Cloud Run remembers each service's build config, so renaming a module breaks nothing today — and then fails the next deploy, months later, looking for a file that no longer exists.

    latent for two months after the July renames

  5. 05

    Streaming inserts don't create their table

    The audit row goes in with insert_rows_json, which — unlike a load job — will not create its destination. A missing table meant the audit row vanished with only an error log, so the observability layer was the broken part and nothing reported it. The code now creates the table itself.

    cost: weeks of silently lost QSM audit history

  6. 06

    Named time zones drift apart

    Three jobs are 20:00 local across Pacific/Easter and America/Denver. They were simultaneous, then an hour apart after a DST change. Anything sharing a refresh-token secret must stay staggered, so new jobs are pinned to Etc/UTC.

  7. 07

    Credential files start life exposed

    Both ignore files used to list credential files by name, so every new dump was committable and uploadable until someone remembered. full-dump.env arrived that way. Now *.env in both, with an explicit .gcloudignore — without one, exclusions are merely inferred from .gitignore.

  8. 08

    A service nobody triggers looks healthy

    quickbooks-prod had no scheduler job and went 61 days without running. A service that never runs never emails a failure, so the absence of runs looked intentional. scripts/pipeline_health.py now flags silence as well as failure — and deliberately flags unscheduled pipelines too, on a longer fuse.

    cost: 61 days of stale PCS invoices

  9. 09

    Silence is the house failure mode

    The SendGrid key died for three weeks while loads succeeded — the only symptom was email that stopped arriving. Then the docs carried it as an open blocker for seven weeks after it was fixed. Verify against the cloud, not the docs.

    Closed on 2026-09-10: pipeline-monitor now watches for absence as well as failure, and signals twice — an email, and a 500 that Cloud Scheduler records whether or not anyone reads mail.

  10. 10

    Zero rows is not always a failure

    Kaya's first run fetched 0 invoices on a 30-day window and 68 on an unbounded one. Nothing had been touched in a month.

  11. 11

    The pipeline a client needs is a measurement, not an assumption

    Half the clients here record no invoices worth syncing, and they are the two largest by revenue. An invoice sync for ODF would run flawlessly forever and return an empty table.

    cost so far: one pipeline built for the wrong entity (Kaya), before the survey existed

09When it breaks

The order matters more than the commands

  1. Read the fleet, not your inbox

    Reads BigQuery through ADC, so it survives a gcloud session hitting its reauth wall. Exits non-zero when anything is failed or silent.

    python scripts/pipeline_health.py

    The same module runs unattended as pipeline-monitor at 06:00 UTC. It emails only when something is wrong, and returns HTTP 500 on any problem so Cloud Scheduler records a failed attempt — so its verdict is visible in gcloud scheduler jobs list without trusting the monitor to email about itself.

  2. Read the error body before deciding anything

    invalid_client and invalid_grant are both 400 and share no fix.

    gcloud logging read 'resource.type="cloud_run_revision"
  AND resource.labels.service_name="qsm-reports"
  AND textPayload:"token refresh failed"' \
  --project=parasoldatalake --limit=5 \
  --format="value(timestamp,textPayload)"

  3. Date the outage from the secret's history

    The gap in the version list is the timeline.

    gcloud secrets versions list qsm-qbo-refresh-token \
  --project=parasoldatalake --limit=10

  4. Redeploy first, if the running revision predates the fixes

    Deploying needs no valid token. Loading a good token onto vulnerable code risks one slow Intuit night undoing the whole recovery.

  5. Then store the token — as one step

    Stores what Intuit returns, not what you pasted, and confirms which company you actually authenticated as. If that name is wrong, stop.

    python scripts/restore_qbo_token.py \
  --secret kaya-qbo-refresh-token \
  --realm 193514758651234 \
  --basic-auth '<Basic blob>' \
  --auth-code '<fresh code, ~10 min fuse>'

  6. Trigger everything and check load counts

    Not secret versions — see section 04.
